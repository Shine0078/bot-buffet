# Authentication and credentials

Development uses `x-bot-buffet-user` only for local testing. Production mode requires a bearer JWT validated against `BOT_BUFFET_OIDC_ISSUER`, `BOT_BUFFET_OIDC_AUDIENCE`, and an HTTPS `BOT_BUFFET_OIDC_JWKS_URI` (or a pinned public `BOT_BUFFET_OIDC_JWKS_JSON` for controlled bootstrap/testing). Only RS256 keys with a matching `kid` are accepted; issuer, audience, authorized party, expiry, not-before, issued-at, optional nonce, and subject are validated before the subject becomes the actor ID. The loopback-only `bootstrap` mode accepts `BOT_BUFFET_BOOTSTRAP_TOKEN` for migration and never uses it as production identity. API keys/OAuth tokens are write-only inputs to the encrypted `CredentialVault` in local mode (or an external KMS/secret manager in production); the application stores provider, auth type, scopes, expiry, disabled state, and a fingerprint—not values. When no development master key is supplied, the vault creates a random 32-byte key beside the credential file with restrictive permissions; this key is not included in backups and must be provisioned separately for restore. Rotation is connect-new → test → switch route → revoke-old → audit.
