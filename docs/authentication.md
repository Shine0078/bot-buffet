# Authentication and credentials

Development uses `x-bot-buffet-user` only for local testing. In production the direct API accepts a bearer token and uses `BOT_BUFFET_API_SUBJECT` as a single configured principal; it deliberately ignores the user header. This is a bootstrap control, not a multi-user identity provider: the owner must terminate OIDC/SSO at the edge, validate issuer/audience/nonce/expiry, map claims to workspace memberships, and enforce RBAC on every route before exposing it to multiple users. API keys/OAuth tokens are write-only inputs to the encrypted `CredentialVault` in local mode (or an external KMS/secret manager in production); the application stores provider, auth type, scopes, expiry, disabled state, and a fingerprint—not values. When no development master key is supplied, the vault creates a random 32-byte key beside the credential file with restrictive permissions; this key is not included in backups and must be provisioned separately for restore. Rotation is connect-new → test → switch route → revoke-old → audit.
